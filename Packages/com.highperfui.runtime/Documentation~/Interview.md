# 资深游戏客户端面试讲述

## 三分钟主线

“我从 SLG 复杂物品 UI 的真实问题出发。循环列表只解决数量，完整 Item 模板仍有很多条件分支，刷新容易全量绑定，池化后异步回调还可能串到其他物品。我把原有按需子树思想迁移为 Unity UPM 包，分成集合、展示增量、片段、调度和生命周期五个协作边界，并提供真实军备业务 Sample，而不是只做性能按钮。”

接着讲清楚三个选择：显式 View 契约胜过透明代理任意 Unity API；字段级状态合并胜过通用树 Diff；跨帧正确性优先于盲目追求每一帧都只花2ms。最后引用交付验证记录，不编造收益。

## 值得准备的追问

| 面试追问 | 应回答到的技术细节 |
|---|---|
| 与对象池/循环列表有什么区别？ | 分别解决实例总数、模板内分支常驻、重复属性同步；主要比较 C/B，不能把循环列表收益全部归给虚拟节点 |
| 为什么不用 React/Fiber？ | Unity 原生副作用、已有 prefab 和身份模型；这里是协作式小步调度，不借名宣称硬抢占 |
| 强化后排序变化怎样不串格？ | index 与稳定 ID 分离；结构重映射保留实例，同时发内容通知刷新同 ID 的新属性 |
| 对象归还后异步图片回来怎么办？ | 请求序号 + BindingGeneration + Scope；归还重租再查 lease；取消不替代校验，丢弃也须释放句柄 |
| 同步实化与预算冲突怎么办？ | 明确 Require 是兜底同步路径；批量小范围才用，批量大树走调度；记录单步 overshoot |
| 第三方动画/监听怎样重置？ | 显式 Scope.Track 和 OnReturn 契约，无法自动推断所有外部副作用 |
| 怎么避免懒加载最后变成全部常驻？ | 空闲池数量上限、可选片段清退；同时验证反复创建导致的 GC，缓存命中率不是唯一目标 |
| 怎么证明优化有效？ | 独立进程、同业务数据/路径、固定设备、足够帧数、多次轮换顺序、语义与像素校验；保留失败及退化 |
| 能直接上商业项目吗？ | 包可直接安装，但属于预发布；机型、IL2CPP、资源系统、布局组合、长时间压测仍须项目验证 |

## 五分钟现场演示

从 Sample 的仓库、筛选、穿戴、强化和奖励领取开始，展示这是共享业务真源。然后打开可选诊断入口，解释 A/B/C 基线。再切到两个有代表性的回归测试：排序后同 ID 内容刷新、回收/重绑后的迟到回调隔离。

不要把功能表念一遍。重点展示一次错误路径如何出现、为何普通实现会错、这里用哪条不变量保证正确，以及代价是什么。

## 不能包装成履历的内容

本 Unity 包是新实现，不等于原商业 SLG 线上使用了这些新增机制；没有实测就不说“GC下降80%”“92%命中率”“1000节点严格2ms”。Windows Mono 测试不代表手机或 IL2CPP，技术复杂度也不保证面试结果。
