# 资深游戏客户端面试：军备 UI 优化

## 从业务问题开始

不要从“我做了 Fiber、Lane、对象池”开始。先说明：仓库数量大，装备卡片随品质、词条、精通、套装、锁定等状态膨胀；仓库、详情和奖励预览共享同一种物品，却有不同显示组合。循环列表解决实例数量，却未解决复杂完整模板的常驻节点、全量绑定及异步复用串数据。

本项目把问题拆成四层：只创建可见卡片；只创建需要的片段；只刷新发生变化的物品和字段；复用后旧任务不得写入新主人。指标必须与 B 循环列表比较，而不是只展示击败 A。

## 可落到代码的设计

| 层 | 实现 | 解决的问题与取舍 |
|---|---|---|
| 业务真源 | InventoryModel、快照、Changed 稳定 ID 通知 | 装备/强化/奖励/存档复用规则；UI 不另外计算一套交易状态 |
| 集合层 | FixedVirtualizedScrollList | 可见范围回收、结构变更按 ID 重映射、内容变更批量定位；列表索引不是业务身份 |
| 片段层 | LazyFragmentHost、依赖描述、RequiredForInteraction | 复杂稀有词条等按需实化；交互必要状态与可延后装饰分开；隐藏可选片段有保留上限 |
| 更新层 | IncrementalUiView、脏字段、调度与提交 | 合并同帧更新、避免重复属性写入；预算是软预算，原生 Instantiate 不能从中间抢占 |
| 生命周期 | Scope、BindingToken、UiLeaseToken、异步资源槽 | 归还重租、同实例重新绑定、销毁时阻断旧回调；当前绑定版本和租约版本含义不同 |
| 验证层 | 指针点击测试、语义摘要、像素检查、独立进程采样 | 不以“截图有内容”代替正确性；不以节点数代替 CPU 或内存收益 |

## 真正值得深挖的困难

1. 排序时索引改变、ID 不变。保留实例可以减少绑定，但强化后即使 ID 不变仍须内容通知；已有专门的失败再修复回归测试。
2. 异步图标晚到。取消只能减少浪费，不能代替提交前核对绑定令牌；供应者故意允许迟到完成，验证消费者是否正确防护。
3. 片段依赖与交互时序。需要交互的片段必须先满足依赖，再开放交互。模板销毁、实化失败和重试必须保持门禁关闭。
4. 池化与内存的矛盾。无限保留可选片段会把“按需”变成滚动后全部常驻；清退太积极又增加创建和 GC。这里给出有界策略，并记录真实代价，不声称总能同时优化所有指标。
5. 奖励和强化不是按钮动画。资源检查、幂等操作、一次性领取、存档校验和备份都在模型层完成；本地校验不等于防作弊或服务端权威。

## 为什么不是更复杂的方案

- 不做通用 Virtual DOM：军备 UI 已有明确物品 ID 和局部状态，通用树 diff 会增加无谓分配和接入成本。
- 不承诺透明代理整个 Unity API：Transform、动画、布局和第三方组件有真实副作用，显式边界更可测试。
- 不把所有工作都切片：首次可交互的关键状态同步保证，后续可合并更新调度；小任务切得过碎可能更慢。
- 不宣称“严格2ms”：单个不可中断原生操作可能越过预算，要观察超预算次数与最大值。

## 面试时的证据边界

引用 ProductBenchmarkReport.md 的实测数字和协议。当前是 Windows Mono Development Player、特定设备和业务切片。B 是完整卡片池化循环列表，不是手写到极限的分类型工厂。只有和 B 的真实收益才证明按需片段这一层的价值；A 的巨大收益主要来自可见列表。

本交付不包含线上接入、移动设备、IL2CPP 验证、长期压力和多人协作维护记录，不能描述成在《指环王：纷争》线上已经取得同样收益。九分是验收目标，不是履历包装或自动评分。
