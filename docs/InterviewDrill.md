# 资深岗位追问演练

## 1. 你这个虚拟节点和循环列表有什么区别？

循环列表解决的是“1000 条业务数据是否要有 1000 个真实 Item”。本框架先承认这个常规方案有效，B 模式就是它。片段虚拟化进一步解决“已经存在的每个 Item 是否必须拥有所有选中、锁定、套装、强化等分支”。未使用分支只有描述和需求，没有 GameObject；需要时才创建。

两者可以组合，但不应混为一项收益。B/A 解释列表虚拟化，C/B 才用于讨论额外结构管理是否值得。

## 2. 你为什么没有直接照搬 React Fiber？

问题不是缺少一个 React，而是 Unity 主线程上的集中创建、重复写入及跨帧归属。当前用小步工作接口、显式依赖和类型化状态解决这些问题，没有全树 Diff、通用协调器或可中断原生对象创建。

复杂度来自能验证的不变量，而不是术语数量。此处称“协作式调度”准确，称“任意抢占”不准确。

## 3. 既然分配了 2ms，为什么还可能 10ms？

预算检查发生在工作项之间。若剩余 0.2ms 时执行一次耗时 3ms 的 Instantiate，无法在其中暂停。引擎后续 Canvas、布局、渲染以及 GC 也不包含在这 2ms 中。

处理顺序是测单步峰值，判断是否值得拆小片段或提前准备，再结合完整帧尾和交互延迟调整预算。更小的预算可能使首屏更慢，不能只追求调度统计好看。

## 4. 同一个格子先绑定 A，后绑定 B，再回到 A，旧请求如何判断？

业务 ID 相同不足以判定有效；绑定代际必须相同，Scope 必须仍存活，图标槽自己的请求序号也必须相同。

三个维度各自防止页面关闭、实例重绑、同绑定内重复请求。旧结果无论是否显示都要释放消费者租约，且不能清空新请求的句柄。取消底层加载不是正确性的前提。

## 5. 为何要把状态和命令分开？

“数字从 10 变为 11 再变为 12”通常可以只显示最终的 12；“播放两次领取反馈”不能简单合并成一次属性写入。状态可以合并，命令有顺序和副作用。

当前命令队列按 Binding 和业务就绪谓词执行，异常不自动重播。但它尚无内置状态版本屏障，不能保证某条命令一定看见某个中间展示版本。需要这种语义的业务应增加明确版本协议，不能只等队列变空。

## 6. 为什么对象池可能把性能问题变成正确性问题？

一个实例被新业务复用，但事件、动画、异步回调可能仍代表旧业务。若 OnEnable 在新 Scope/Binding 准备前发生，旧逻辑会观察到错误状态。所以先在 inactive 根下准备，再激活；归还先失效，再清理。

还必须区分引用归属和租借代际。本版能检查错误池和重复归还，但没有 Pool LeaseId；过期回调不能直接调用 Return(view)。这不是“池越复杂越好”，而是要明确允许谁归还谁。

## 7. 你怎样证明测试不是自说自话？

不让格子自己报告自己的 ID 就算成功。测试从预期集合索引反查 Model，验证覆盖数量、ID 唯一性、名称/等级/战力、图标及片段显隐。PlayMode 通过实际 GraphicRaycaster 和 PointerClick 进入按钮，不仅直接调用 Equip 函数。

Player 使用相同数据种子和脚本，最后比较业务摘要并截取真实画面，网格 ROI 要有内容。独立进程轮次必须齐全；超时、非零退出、黑屏和语义差异都使批量验证失败。

仍然有限：图像丰富度不等于像素级视觉正确，当前没有移动真机自动触控，也没有完整多场景性能 SLA。保留这些边界比“100% 正确”更可信。

## 8. 如果 C 比 B 慢，项目是不是失败了？

先区分问题。若目标是降低单元结构驻留，C 减少节点可能有价值；若页面主要压力只是数据很多，B 已足够，C 的管理和调度等待就是额外成本。

本次不预设 C 胜出。参考实测说明适用条件，再决定接入策略：可选子结构昂贵的热点用 C，简单固定 Item 用 B。当前帧率上限附近的细小帧时间差不能证明真实 CPU 优势。

```text
        |
        +--> 目标状态 --> Dirty 合并 --+
        |                             |
        +--> 有序命令 --> 就绪判断 ----+--> Scheduler 小步执行
                                      |          |
Binding + Scope + 请求序号 ------------+          +--> 原生实例 / 字段写入
                                                 |
池归属与释放契约 <------------------------- 状态 + 关键片段 + 布局
                                                 |
                                               交互开放
```

讲述时先从一个可复现错误进入，再落到图中的边界和测试。不要只背模块名单。本人参与和工具辅助过程如实说明；没有在线上发生过的案例，称为“故障注入用例”，不包装成线上事故。
