# 用这份 Package 讲清高级客户端工程能力

## 项目定位

这是“复杂 UGUI 的按需展示与生命周期框架”，不是另写一套游戏引擎。真实载体是军备整备业务；Runtime 不知道金币、强化、武将或奖励。最值得讲的不是模块数量，而是为何原优化在池化、异步、排序、跨帧后仍然正确。

不要将新增 Unity 实现说成原商业 SLG 已上线的全部机制。可以准确区分：原项目启发、迁移设计、这次实现、这次验证、尚未完成的商业验证。

## 业务问题如何拆解

| 现象 | 根因 | 选择 | 不解决什么 |
|---|---|---|---|
| 长列表打开卡顿/对象过多 | 全量实例与布局 | 固定高度可见窗口 + 有界池 | 不解决单个 Item 内的冗余分支 |
| 循环列表仍很重 | 通用 Item 装入所有条件展示 | 显式可选片段与依赖图 | 不代理任意 Transform API |
| 一个属性变动导致重复刷新 | 没有区分结构、内容和字段 | 稳定 ID 通知 + 类型化目标状态 + dirty mask | 不代替业务事务或支付命令 |
| 快速滚动串图/串状态 | 实例复用，异步回调仍认旧身份 | Scope、绑定代际、请求序号、租约 | 取消不能保证外部请求真的停下 |
| 调度后按钮偶发点错 | 创建、状态和布局未一起就绪 | 明确 Commit/readiness 与交互门禁 | 不声称多 View 全局原子提交 |
| 优化难迁移/难证实 | 业务与基础设施混在一起 | UPM Runtime 独立，可选 Sample 和测试 | 可安装不等于任何项目零成本接入 |

## 三个最有价值的难题

### 1. 为什么一个取消令牌还不够

业务 ID 相同也可能是再次绑定；同一实例也可能已经归还又重租。请求取消后，底层资源提供者仍可能返回。把这些状态压缩成一个 bool 会出现 ABA 类问题。

框架区分位置 index、业务 DataId、BindingGeneration、LeaseId、Scope token 和资源请求序号。回调应用之前校验当前身份，迟到结果不应用但必须释放资源句柄。旧租约也不能直接执行 Return(view)，因为该 API 本身不接受 token；项目适配器必须先验证 CaptureLease。讲清这个限制，比泛称“线程安全对象池”更可信。

代码阅读顺序：`Runtime/Lifecycle/PooledUiView.cs`、`Runtime/Lifecycle/UiScope.cs`、`Runtime/Assets/AsyncSpriteSlot.cs`，再看对应 EditMode 生命周期/资源测试。以 Source 中实际目录为准，不需要背术语。

### 2. 为什么结构刷新不等于内容刷新

强化后排序改变，旧 index 的实例不一定还属于原物品。按 index 复用会串数据；全部销毁重建又浪费已有实例。按稳定 ID 重新映射可以保留实例，但同一个 ID 的战力已经改变，所以仍需要内容通知。

`RefreshStructure` 处理可见 ID/索引映射；`RefreshItems` 处理变更 ID；派生 View 再以字段 mask 应用差异。RefreshItems 的一次集合构建加活跃扫描为 O(变更数 + 活跃数)，而不是每个变更 ID 扫全量数据。代价是业务必须提供稳定 ID 和可靠变更通知，这也是“低侵入”而非绝对“零侵入”。

重点演示排序后同 ID 保留实例但属性更新的回归测试，以及批量刷新只影响可见相关项。

### 3. 为什么实化之前和之后都要验证绑定

Instantiate、SetActive、OnEnable/OnDisable 可能触发项目代码重入；校验之后并不等于接下来这段执行仍属于原绑定。尤其是先隐藏旧片段再捕获身份，会把隐藏回调触发的新绑定误当成旧请求的身份。

`LazyFragmentHost.RequireVisibleState` 在可触发回调的操作前捕获身份，在隐藏和创建阶段重新校验。单次需求集重建、依赖顺序、队列取消、异常门禁需要一起考虑。`ImmediateFragmentTests` 中的 OnDisable 回归夹具明确断言重绑已发生，然后验证旧请求不能继续实化。

## 选型与取舍

- 用显式片段描述和业务 View，而不是透明包装所有 Unity API：保留 prefab 和原生组件生态，可诊断；代价是需要适配。
- 用字段 mask 与类型化目标状态，而不是反射式通用树 Diff：变更路径可控、分配低、语义明确；代价是需要声明字段。
- 用4:3:2:1加权协作调度，而不是“真正抢占”：只能在小步骤之间让出，原生 Instantiate 不可中断；必须报告最大单步。
- 同步 Require 留作显式兜底：即时业务需求能得到结果，但突破预算。不能用 Require 批量实化大树还承诺2ms。
- 池大小和隐藏片段清退是内存/重复创建的权衡，不是命中率越高越好。本次 C 的更少节点伴随更多分配，正是下一轮缓存消融的输入。
- 不自带 Addressables 全家桶：接口隔离让项目选择资源系统，但生产适配器要负责主线程回调、句柄释放及取消语义。

## 十分钟演示路径

1. 先运行军备 Sample，筛选、穿戴、强化、领奖，再退出/重进验证进度。不要先打开性能面板。
2. 打开“性能对照”，解释 A 全量、B 循环池化、C 按需增量。快速比较只是功能预检，不代替独立进程报告。
3. 展示 ValidationResults.md 的实际 B/C 数据，同时展示 C 首屏/分配退化与 A 不完整尝试。
4. 打开稳定 ID 刷新和迟到回调两个回归测试，说明优化如何引入错误、用什么不变量防止它。
5. 打开 package.json、Runtime asmdef、独立安装证据，说明怎样接入已有项目、灰度替换一个重 Item、如何退回原完整 prefab。
6. 最后列生产门槛：真机、IL2CPP、长期压测、真实资源系统、项目 UI 适配。不要用“9分”代替这些证据。

## 评价标准

可作为高级客户端面试的可运行工程材料：有问题拆解、选型、生命周期一致性、失败路径测试、包边界、实测与反例。资深程度取决于能否解释上述代码和代价、能否在真实项目验证收益，而不是念出 Lane/Fiber/三阶段 Commit 等名称。
