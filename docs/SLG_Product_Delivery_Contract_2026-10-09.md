# SLG 军备整备中心产品与交付规格

日期：2026-10-09。目标：可运行、可完整操作、可验证性能收益，并能作为资深游戏客户端面试项目。状态：产品交付规格，新增业务与升级内核尚未据此实现。

## 1. 最终交付是什么

交付一个 Unity UGUI 单机业务应用“SLG 军备整备中心”，打开就进入可操作的游戏界面，不以技术概念按钮或测试面板作为主画面。

以现有 HighPerfUI Unity 装备工程为基础继续升级，保留框架 Package、现有业务和实验记录。原《指环王：纷争》代码作为复杂通用组件、奖励和交易路径的设计依据；业务数值与美术采用独立演示内容，不宣称复刻原游戏全部玩法。

这不是一款完整 SLG，也不额外建设战斗、地图、联网服务器。完整性体现在明确范围内的业务闭环和交付质量，而不是做几十个只有空壳的系统。

## 2. 玩家能完成的业务闭环

```text
活动奖励领取
  -> 混合物品入库与资源增加
  -> 仓库分类、搜索、筛选、排序
  -> 选装备，与当前穿戴装备比较
  -> 消耗资源强化，确认或取消
  -> 穿戴/替换，更新槽位、战力与套装展示
  -> 锁定重要装备，处理可操作状态
  -> 退出并重开，恢复业务存档
```

各步影响同一份权威业务状态。奖励领取不是单纯播放动画；强化不是无条件增加一个数；套装不能用随机 ID 规则假装业务含义。

### 2.1 页面与布局

| 界面 | 应有内容与操作 |
| --- | --- |
| 军备仓库 | 混合物品网格、分类/品质/锁定筛选、搜索、排序、选中、空态；大量数据下仍可正常滚动 |
| 装备整备 | 六个穿戴槽、当前总属性、装备对比、强化成本与上限、资源不足、锁定；详情中的精通/套装等按需展示 |
| 活动奖励 | 未领取/已领取状态、混合奖励预览、领取确认、入库结果；重复点击不重复发奖 |
| 性能对照 | 独立入口；对同一业务轨迹运行合理基线与虚拟节点模式，输出结果与差异说明 |

主页面使用熟悉的游戏业务信息与图标，不把 Binding、Lane、Fiber 等术语放在玩家操作区域。技术状态只出现在专门的性能与诊断视图。

仓库、整备、奖励共享一个组件展示体系。不是三个独立静态 demo，也不在正常操作中强迫用户选测试参数。

### 2.2 演示数据

- 日常默认数据量以界面可用性和实际结构分布为准，不用 1000 项作为所有页面的固定业务需求。
- 另提供 1000/5000 项的容量压力轨迹；全量模式可以有明确保护上限，超出时显示中止结果，不能静默减少数据。
- 资源、普通道具、装备、英雄奖励外观、带时效物品等使用有差异的展示结构。
- 精通进度、套装关系、时效、锁定等有独立字段和规则，不靠 ID 取模制造功能。
- 不生成大量永远不会使用的重分支以人为放大收益。记录真实演示业务中的结构使用比例。

## 3. 业务正确性要求

### 3.1 状态与命令

业务状态与 UGUI 对象分离，但不建设泛用 MVVM 平台。采用局部 Domain Store 和显式业务命令：领取、强化、穿戴、锁定。

每条命令先校验条件，再一次提交其相关状态，最后通知受影响视图。例如强化同时更新货币、等级和属性；资源不足时这些状态都不改变。选中物品用稳定 ID 表示，排序后不会变成另一件装备。

### 3.2 保存与失败行为

- 本地存档包含版本和必要业务状态；演示模式可重置，正常模式不会每次启动重新随机覆盖存档。
- 保存采用临时文件与安全替换策略，损坏存档有可见恢复行为；不能直接无提示吞异常。
- 强化确认重复点击只提交一次；奖励领取以奖励记录 ID 防止重复处理。
- 弹窗取消不扣资源，切页不遗留无法关闭的遮罩，关闭应用后恢复状态。
- 本期没有真实服务端。延迟/失败/乱序测试通过可替换提供器模拟，不能宣传为线上网络可靠性证明。

## 4. 技术深度如何与业务绑定

| 技术难点 | 必须出现的业务触发 | 应交付的解决能力 |
| --- | --- | --- |
| 一个通用模板承载不同复杂结构 | 普通资源与套装装备、精通、时效奖励混排 | 类型轻量模板优先，长尾结构按需实化；结构使用和成本可归因 |
| 路径访问误触创建 | 初始化隐藏分支、打开装备详情 | 明确 Peek/Require 语义与方法支持表；未知原生操作局部回退 |
| 复用后结构/状态残留 | 装备 -> 资源 -> 英雄奖励 -> 装备的循环单元 | 干净结构画像、有界缓存、完整 reset，不能直接复制活跃实例作为新模板 |
| 更新影响多个视图 | 强化后仓库、穿戴槽、详情、资源栏同时变化 | 字段变更集与受影响视图索引；不以重新绑定全页作为默认实现 |
| 更新改变当前排序 | 按属性排序时强化选中装备 | 稳定 ID、位置与内容变化区分、滚动锚点及选择不串台 |
| 高频请求晚到 | 快速切选、滚动复用、详情关闭与重开 | BindingGen、LeaseId、字段请求 Revision；过期结果清理所有权 |
| 隐藏结构依赖动画/布局 | 精通与奖励展示动画 | 依赖闭包与安全岛；就绪后发布，不用空白内容伪装可交互 |
| 分帧与输入竞争 | 准备较重奖励结构期间操作前台 | 只在明确可异步阶段拆步，记录原生超支；前台操作不被后台预热拖住 |
| 缓存减少创建却增加占用 | 多类型奖励反复打开 | 缓存预算、清理失败退出、长期驻留对照，报告节点与资源不同口径 |
| 框架接入成本 | 现有业务工厂与独立最小项目 | 可安装 UPM Package；业务层不依赖调度内部；按合同统计接入改动 |

不为“看上去复杂”额外做通用 Fiber、完整声明式渲染器或新资源系统。上述问题已经足以形成多层架构，且每层都必须能在可运行业务中触发与验证。

## 5. 正常业务与性能对照的关系

正常模式默认运行经验证的优化路线。用户可以不懂虚拟节点也完成所有业务。

性能入口提供：

1. 同一业务结果、同一数据、同一轨迹的对照。
2. 完整模板、常规列表/池、类型轻量方案与候选虚拟方案的有效比较。对照可以组合共享基础优化，必须公开配置。
3. 首屏可交互、克隆/绑定 CPU、场景 P95/P99、节点、分配、实例/资源占用及长帧原因。
4. 冷/热打开、滚动、强化联动、奖励领取、首次展开详情分别报告，另列压力轨迹。
5. 真实数值和原始记录，不显示预设优化百分比；候选退步也必须显示。

内置对照用于直观演示。正式性能报告仍使用独立进程轮换运行，避免先运行的模式给后运行模式预热资源；不把用户刚切换模式的几帧当正式成绩。

正确性防护不作为可关闭的“加速选项”。性能实验不能关闭版本校验或清理来获取好看的数字。

## 6. 九分目标的验收依据

“九分”指下面明确维度中的高质量交付目标，不是已经取得的成绩，也不代表面试官会给相同分数。

| 维度 | 满分 | 高质量要求 |
| --- | ---: | --- |
| 业务完整性 | 2 | 领取、入库、筛选、比较、强化、穿戴、保存形成闭环，失败与边界可操作 |
| 架构与技术深度 | 2 | 支持范围清晰；访问语义、结构复用、版本一致性、所有权与依赖有实现和测试 |
| 性能价值与证据 | 2 | 在真实业务轨迹相对最佳合理基线有显著收益，代价公开，可复现并有归因 |
| 正确性与工程可靠性 | 2 | 真实点击、类型切换、乱序、关闭重开、长期驻留、包安装等验证通过 |
| 视觉与操作体验 | 1 | 完整游戏业务界面、真实图标/素材、排版清楚，玩家无需读技术说明即可操作 |
| 交付与面试材料 | 1 | 可执行程序、工程、Package、操作指南、实验记录与技术叙述齐全 |

目标至少达到 9/10，同时不能有阻断项：业务闭环未完成、候选相对最佳基线没有值得推广的收益、运行/点击错误、状态串台、假数据、关键交付缺失。不能用文档或美术得分抵消这些阻断项。

性能准入建议沿用架构设计的候选门槛：克隆与绑定 CPU 降低 30% 或可归因 UI 实例峰值占用降低 40%，且首屏/输入 P95 不劣化超过 5%。正式测试前根据设备与预实验冻结；它们不是现有工程成绩。

如果收益不够，先调整模板、代理开销和接入场景；必要时采用轻量类型模板作为部分业务的最终实现，不把全 UI 使用虚拟节点当成功条件。

## 7. 最终交付目录

继续在 `D:/SLG/HighPerfUI` 交付，升级版单独标记版本，保留旧报告与现有可运行版本以便比较。

```text
Builds/<version>/Windows/       可直接运行的 exe 与完整依赖
ReferenceProject/              Unity 业务工程与可打开场景
Packages/com.highperfui.runtime/框架源包
Deliverables/                  完整压缩包与可安装 Package
Benchmarks/<version>/          原始数据、摘要、截图与失败记录
docs/                          操作、集成、架构、实验与面试材料
```

面试材料包括 3 分钟叙述、10 分钟深入讲解、关键源码入口、技术选型理由、失败案例与当前限制。实验与架构内容服务于可运行产品，不替代产品交付。

演示场景不依赖开发机绝对路径；压缩包在新目录解压后启动验证。UPM 包在干净 Unity 工程单独安装验证，不能只在参考工程里能编译。

## 8. 实施顺序

1. 保留现有工程、数据与可执行版本；冻结旧基线。
2. 先完成仓库/整备的真实业务规则、稳定 ID 和存档，再增加奖励入库闭环。
3. 按上述业务所需升级虚拟节点内核：访问契约、复杂片段、结构画像、精准更新与复用安全。
4. 完成奖励、详情等结构的依赖与显式准备，不强制所有 UI 都进入分帧调度。
5. 完成游戏界面表现和输入体验，独立提供性能对照入口。
6. 执行分场景、公平基线与生命周期验证，调整负收益路径。
7. 构建、解压启动、独立 Package 安装，交付代码、程序、数据与面试材料。

每阶段都有可运行验证，不以“先完成全部底层研究，再考虑界面”推进。只有整体完成验收后才称为本规格交付完成。

## 9. 当前状态

- 现有可执行装备工程已经存在，但只代表前一版能力。
- 本规格明确了新增业务、复杂结构、性能证据和交付标准。
- 新业务闭环和升级内核尚未按本规格实现，不将现有 exe 标成九分版本。
- 原项目复杂资产与真实客户端尚未具备，Unity 业务应用可以独立实现；原游戏线上收益仍需另行验证。

详细访问语义、生命周期、成本模型及选型依据见 [升级架构设计](D:/SLG/HighPerfUI/docs/SLG_VirtualNode_Business_Architecture_2026-10-09.md)。
